# Деплой клієнта на Vercel

Що треба зробити один раз, щоб джоба `Deploy · client (staging)` запрацювала.

Три кроки в панелі Vercel і один секрет у GitHub. Токен не потрібен.

## 1. Проєкт у Vercel

| Налаштування | Значення | Зараз |
|---|---|---|
| Root Directory | `client` | ✅ |
| **Framework Preset** | **Next.js** | ❌ стоїть `Other` |
| Node.js Version | `22.x` (як у `.nvmrc`) | ⚠️ стоїть `24.x` |
| Build Command | за замовчуванням | ✅ |

`Framework Preset = Other` — причина, чому останній деплой віддає 404 на все:
Vercel не знає, що це Next.js, і роздає `client/public` як статику. У
`client/vercel.json` є `"framework": "nextjs"`, і він має це перекрити, але
поле в панелі краще виставити явно — щоб два джерела правди не розходились.

Автодеплой Git-інтеграції вимкнено файлом `client/vercel.json`
(`git.deploymentEnabled: false`), а не кліком у панелі. Причина та сама, що й
для `server/fly.toml`: налаштоване кліками не знає ніхто, крім того, хто
клікав. У файлі це видно на рев'ю і відкочується разом з рештою.

На deploy hook це не впливає: `deploymentEnabled` вимикає деплой **на коміт**,
а hook — явний тригер.

## 2. Вимкнути Deployment Protection

*Settings → Deployment Protection → Vercel Authentication → **Disabled***.

Поки вона увімкнена, будь-яка адреса деплою віддає 302 на `vercel.com/sso-api`
замість сторінки. Це ламає дві речі одразу: сайт не бачить ніхто без входу в
акаунт Vercel, і CI не може перевірити, що деплой доїхав, — він отримує
редирект замість відповіді.

Перевірити:

```bash
curl -sI https://mockup-all1ins-projects.vercel.app | head -1
```

Має бути `HTTP/2 200`, а не `HTTP/2 302`.

## 3. Створити deploy hook

*Settings → Git → Deploy Hooks*:

| Поле | Значення |
|---|---|
| Hook Name | `github-actions` |
| Git Branch Name | `momot-main` |

Кнопка **Create Hook** видасть URL виду:

```
https://api.vercel.com/v1/integrations/deploy/prj_…/…
```

На відміну від токена, він показується не один раз, а лежить у цьому списку
завжди — можна скопіювати будь-коли.

## 4. Секрет у GitHub

*Settings → Secrets and variables → Actions → New repository secret*:

```
VERCEL_DEPLOY_HOOK_URL
```

Один. `VERCEL_TOKEN`, `VERCEL_ORG_ID` і `VERCEL_PROJECT_ID` більше не
використовуються — їх можна видалити.

> URL деплой-хука — це секрет. Хто його має, той може запускати збірки.

## Як це працює

```
push у momot-main
  └─ усі перевірки зелені
      └─ Deploy · staging      (бекенд на Fly)
          └─ Deploy · client   (POST на hook → Vercel збирає)
              └─ чекаємо, поки /api/version віддасть цей коміт
```

### Чому hook, а не Vercel CLI

Спершу тут стояв CLI: `vercel pull` + `build` + `deploy --prebuilt`. Схема
правильніша — артефакт народжується в CI, — але вона тримається на токені.
Токен показується один раз, не відновлюється, а три різні поломки (не той тип
токена, не той scope, не та команда) дають однаково непрозорі повідомлення.
Витрачений на це час перевищив вартість усієї джоби.

Deploy hook — просто URL, який приймає POST. Не протухає, лежить у
налаштуваннях, копіюється будь-коли. Ціна: збирає Vercel у себе, а не ми. Для
клієнта це прийнятно — на відміну від бекенда, тут немає образу, який має бути
побайтово тим самим у всіх середовищах.

Гейт зберігається повністю: джоба не дійде до hook, поки `summary` червоний.

### Чому чекаємо на конкретний коміт

`client/src/app/api/version/route.ts` віддає `VERCEL_GIT_COMMIT_SHA` тієї
збірки, яка зараз у проді. CI чекає, поки там з'явиться його `GITHUB_SHA`.

Перевірка «сайт відповідає 200» тут не працює: стара версія відповідає весь
час, поки Vercel збирає нову. Вона зеленіла б миттєво й підтверджувала б
попередній деплой.

### Звідки береться адреса бекенда

`BACKEND_URL` задано в `client/vercel.json` (`build.env`), бо збірка тепер
відбувається на боці Vercel. `next.config.ts` читає його під час білду й
запікає в rewrites — тобто адреса фіксується в артефакті назавжди.

У файлі, а не в панелі Vercel: так її видно на рев'ю і вона змінюється разом
з кодом.

Клієнт не ходить у бекенд напряму з браузера — Next проксює запити на своєму
боці. Через це куки бекенда (`httpOnly`, `sameSite: strict`) лишаються
робочими: браузер бачить їх як куки того ж сайту, що й сторінка.

## Відкат

Окремого коду немає й не потрібно: Vercel зберігає кожен деплой.

*Deployments → потрібний деплой → **Promote to Production***.

Для бекенда відкат довелось писати руками (`ci.yml`, крок `Roll back to the
last working image`), бо Fly такого не має.

## Якщо деплой падає

| Крок | Що зламано |
|---|---|
| `Check the deploy hook is configured` | секрету немає, або в ньому не URL хука, або туди заїхав перенос рядка |
| `Trigger the Vercel build` | hook відповів помилкою — найчастіше видалений у панелі |
| `Wait for this commit to go live` | збірка впала, або увімкнена Deployment Protection, або hook прив'язаний не до тієї гілки |

Останній рядок — найпідступніший. Якщо збірка в панелі зелена, а крок усе одно
падає, перевіряй у такому порядку:

1. `curl -sI https://mockup-all1ins-projects.vercel.app | head -1` — якщо 302,
   вмикається Deployment Protection (крок 2 вище);
2. hook створений для гілки `momot-main`, а не `main`;
3. `curl -s .../api/version` — якщо `{"commit":"unknown"}`, збірка йшла не з
   Git, і `VERCEL_GIT_COMMIT_SHA` порожній.

## Після першого успішного деплою

Адресу клієнта треба прописати бекенду — зараз там локальна:

```toml
# server/fly.toml
FRONTEND_URL = 'http://localhost:3001'   # ← замінити на адресу з Vercel
```

Це не косметика. `FRONTEND_URL` використовується для CORS і для повернення
після OAuth-логіну; поки там `localhost`, вхід через Google і Facebook на
живому сайті не завершиться.

## Відомі розбіжності

| Що | Зараз | Має бути | Наслідок |
|---|---|---|---|
| Production Branch | `main` | `momot-main` | Гілки `main` у репозиторії немає. На hook не впливає — він має власне поле гілки |
| Node у Vercel | `24.x` | `22.x` (`.nvmrc`) | Збірка на Vercel піде на 24, тоді як CI перевіряє код на 22 |
| Домен `mockup-gray-alpha.vercel.app` | 404 | — | До нього не прив'язаний жоден деплой; робоча адреса `mockup-all1ins-projects.vercel.app` |
