# Деплой клієнта на Vercel

Що треба створити один раз, щоб джоба `Deploy · client (staging)` запрацювала.

> Зробіть це **до** мержу PR, який додає джобу. Вона виконується лише на push
> у `momot-main`, тож на самому PR не запуститься й нічого не покаже — а перший
> же ран після мержу впаде на перевірці секретів.

## 1. Проєкт у Vercel

Створити проєкт з цього репозиторію і виставити одне налаштування, у якому
найлегше помилитись:

| Налаштування | Значення |
|---|---|
| Root Directory | `client` |
| Framework Preset | Next.js |
| Build Command | за замовчуванням |

**Git-інтеграцію треба вимкнути.** У налаштуваннях проєкту, розділ *Git*, зняти
автодеплой для `momot-main`. Інакше Vercel деплоїтиме на кожен push самостійно,
повз усі перевірки — тобто фронт їхатиме у продакшн навіть із червоним CI. Саме
щоб цього не сталося, деплой і винесений у воркфлоу.

## 2. Три значення

**`VERCEL_ORG_ID` і `VERCEL_PROJECT_ID`** — з'являються у файлі `.vercel/project.json`
після `vercel link` у теці проєкту. Або на сторінці проєкту: *Settings → General*
(Project ID) і *Settings* команди (Team ID).

**`VERCEL_TOKEN`** — *Account Settings → Tokens → Create*. Scope обмежити тією
командою, якій належить проєкт, а не давати доступ до всього акаунта.

## 3. Секрети в GitHub

*Settings → Secrets and variables → Actions → New repository secret*, три штуки
з тими самими іменами:

```
VERCEL_TOKEN
VERCEL_ORG_ID
VERCEL_PROJECT_ID
```

## 4. Після першого успішного деплою

Vercel видасть постійну адресу виду `https://<проєкт>.vercel.app`. Її треба
прописати бекенду — зараз там стоїть локальна:

```toml
# server/fly.toml
FRONTEND_URL = 'http://localhost:3001'   # ← замінити на адресу з Vercel
```

Це не косметика. `FRONTEND_URL` використовується для CORS і для повернення після
OAuth-логіну; поки там `localhost`, вхід через Google і Facebook на живому сайті
не завершиться.

## Як це працює

Клієнт не ходить у бекенд напряму з браузера. `client/next.config.ts` описує
rewrites: браузер б'є в Next тим самим походженням, що й сторінка, а Next уже
проксює запит у `BACKEND_URL` на своєму боці.

Через це куки бекенда (`httpOnly`, `sameSite: strict`) лишаються робочими —
браузер бачить їх як куки того ж сайту, що й сторінка. Якби клієнт ходив у
`mockup-staging.fly.dev` напряму, `sameSite: strict` відкидав би їх при кожній
навігації, і сесія розсипалась би.

`BACKEND_URL` задається у воркфлоу на кроці збірки, а не в панелі Vercel:
`next.config.ts` читає його під час білду й запікає адресу в rewrites. Тобто
значення визначає артефакт назавжди — і місце йому в git, де його видно на
рев'ю, а не в чужій панелі, куди ніхто не заглядає.

## Відкат

Окремого коду для відкату тут немає й не потрібно: Vercel зберігає кожен деплой.

```
vercel rollback --token=<TOKEN>
```

Повертає попередній миттєво. Для бекенда відкат довелось писати руками
(`ci.yml`, крок `Roll back to the last working image`), бо Fly такого не має.

## Що вже налаштовано і як це перевірено

Проєкт `mockup` у Vercel створений, `Root Directory = client` виставлений
правильно. Перевірено запитом до API проєкту, а не на слово.

Автодеплой Git-інтеграції вимкнено файлом `client/vercel.json`
(`git.deploymentEnabled: false`), а не кліком у панелі. Причина та сама, що й
для `server/fly.toml`: налаштоване кліками не знає ніхто, крім того, хто
клікав. У файлі це видно на рев'ю і відкочується разом з рештою.

Vercel застосовує нову конфігурацію починаючи з наступного деплою — тобто
перший після мержу ще може приїхати від Git-інтеграції.

## Відомі розбіжності

| Що | Зараз | Має бути | Наслідок |
|---|---|---|---|
| Production Branch | `main` | `momot-main` | Гілки `main` у репозиторії немає; на деплой з воркфлоу не впливає, бо `--prod` не залежить від цього поля |
| Node у Vercel | `24.x` | `22.x` (`.nvmrc`) | Збірка йде в CI на 22, а серверлес-функції стартують на 24 |
