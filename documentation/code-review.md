# CODE REVIEW GUIDE — Standard Review

**Frontend Team | v1.0 | 2026**

---

## 1. Мета та філософія

Code review — це не перевірка «правильно/неправильно». Це спільна робота команди над якістю продукту. Мета рев'ю — зловити баги до продакшну, поширити знання про кодову базу, підтримати єдиний стиль коду та допомогти автору вирости як розробнику.

Рев'ю — це розмова двох професіоналів, а не суд. Тон коментарів має бути конструктивним. Ми не критикуємо людину — ми покращуємо код.

> **Головний принцип**
> Код після рев'ю має бути кращим, ніж до нього. Не ідеальним — а кращим. Не блокуй PR через стилістичні дрібниці, якщо автоматизація (linter, formatter) їх не ловить.

---

## 2. Коли використовувати Standard Review

Standard Review — це основний тип рев'ю, який покриває більшість щоденних задач. Він підходить для:

- Нові фічі середнього розміру (до ~500 рядків змін)
- Рефакторинг існуючого коду
- Виправлення багів (не критичних hotfix)
- Зміни в бізнес-логіці компонентів
- Інтеграції з API та сервісами

Для дрібних змін (typo, config) використовуй Quick Review. Для критичних змін (архітектура, міграції, security) — Deep Review.

---

## 3. Перед початком рев'ю

### 3.1 Що перевірити до відкриття коду

1. **Прочитай опис PR/MR.** Зрозумій, яку задачу вирішує автор. Якщо опису немає або він незрозумілий — попроси автора доповнити перед рев'ю.
2. **Глянь на linked ticket/issue.** Переконайся, що розумієш acceptance criteria.
3. **Перевір CI/CD статус.** Якщо pipeline червоний — не починай рев'ю, поверни автору.
4. **Оціни розмір.** Якщо PR > 500 рядків — попроси автора розбити на менші частини, або переходь на Deep Review.

### 3.2 Чекліст автора PR (що має зробити автор до запиту на рев'ю)

- Self-review пройдено (автор перечитав свій diff)
- Лінтер та форматтер пройшли без помилок
- Тести додані або оновлені
- Console.log та дебаг-код видалені
- PR description заповнений зрозуміло
- Скріншоти/відео додані для UI-змін

## 4. Процес Standard Review

### 4.1 Перший прохід: загальна картина (5–10 хв)

Не кидайся одразу в деталі. Спочатку зрозумій структуру змін:

- Подивись на список змінених файлів. Чи логічно вони згруповані?
- Чи немає змін у файлах, які не повинні бути частиною цього PR?
- Чи відповідає архітектурний підхід тому, як ми вирішуємо подібні задачі?
- Чи не порушує зміна існуючі патерни проєкту?

### 4.2 Другий прохід: детальний аналіз коду (15–25 хв)

Тепер переходь до конкретних файлів. Дивись зверху вниз — від компонентів до утиліт.

#### Логіка та коректність

- Чи правильно працює код для основного сценарію (happy path)?
- Чи оброблені edge cases: null, undefined, пустий масив, мережева помилка?
- Чи немає race conditions в асинхронному коді?
- Чи правильно працює error handling? Чи не «ковтаються» помилки мовчки?

#### React / Angular / Framework-специфічне

- Чи оптимально використовуються хуки (правильні залежності в useEffect, useMemo, useCallback)?
- Чи не створюються зайві ре-рендери?
- Чи правильно управляється стейт? Чи не дублюється він?
- Чи немає прямої маніпуляції DOM там, де фреймворк це робить сам?

#### TypeScript

- Чи використовуються конкретні типи замість any?
- Чи немає type assertions (as) без вагомої причини?
- Чи адекватно названі інтерфейси та типи?

#### Читабельність та підтримуваність

- Чи зрозумілі назви змінних, функцій, компонентів без додаткового контексту?
- Чи не занадто великі функції/компоненти? Може варто розділити?
- Чи немає магічних чисел та рядків? Використовуй константи.
- Чи є коментарі до складної логіки (а не до очевидного коду)?

### 4.3 Третій прохід: тести та безпека (5–10 хв)

- Чи покривають тести основні сценарії?
- Чи тестуються edge cases та error scenarios?
- Чи немає XSS-вразливостей (innerHTML, dangerouslySetInnerHTML)?
- Чи не потрапляють sensitive дані в логи або localStorage?
- Чи валідуються вхідні дані від користувача?

## 5. Як писати коментарі

### 5.1 Категорії коментарів

Кожен коментар має бути позначений префіксом, щоб автор одразу розумів пріоритет:

| Префікс | Значення | Приклад |
|---|---|---|
| **[blocker]** | Критична проблема, без виправлення — не мержимо | "[blocker] Тут можливий memory leak — useEffect не повертає cleanup функцію" |
| **[must-fix]** | Потрібно виправити, але не критично | "[must-fix] Бракує обробки помилки при fetch" |
| **[suggestion]** | Пропозиція покращення, на розсуд автора | "[suggestion] Можна спростити через optional chaining" |
| **[question]** | Щось незрозуміло, потрібне пояснення | "[question] Навіщо тут setTimeout? Яку проблему це вирішує?" |
| **[nit]** | Дрібниця, не блокує мерж | "[nit] Назва isData не описує, що саме це за дані" |
| **[praise]** | Гарне рішення, варте уваги | "[praise] Класна абстракція, буде зручно перевикористовувати" |

### 5.2 Правила хороших коментарів

**Пропонуй рішення, а не просто критикуй.** Замість «це погано» напиши «розглянь варіант X, бо він вирішує проблему Y».

**Будь конкретним.** Замість «тут щось не так з типами» напиши «Prop X має тип string, але компонент Y очікує number».

**Поясни «чому», а не тільки «що».** «Цей useEffect потребує cleanup, тому що при unmount компонента підписка на WebSocket залишиться активною і буде memory leak».

**Не змішуй стиль з логікою.** Стилістичні нюанси — у [nit], логічні проблеми — у [must-fix] або [blocker].

> **Золоте правило коментування**
> Перед тим як написати коментар, перечитай його очима автора. Якщо б тобі це написали — ти б зрозумів і не образився? Якщо ні — перефразуй.

## 6. Тайминг та SLA

| Метрика | Standard Review |
|---|---|
| Час відповіді (перша реакція) | До 4 робочих годин |
| Час на саме рев'ю | 25–45 хвилин |
| Максимум раундів | 2–3 (якщо більше — обговоріть голосом) |
| Розмір PR (рекомендований) | 100–500 рядків |

Якщо рев'ю затягується на більш ніж 3 раунди — це сигнал, що потрібен дзвінок. Запланируй 15-хвилинний кол з автором, погоджуйте рішення усно, а потім зафіксуйте результат у PR.

---

## 7. Рішення після рев'ю

### Approve

Код готовий до мержу. Дрібні [nit] можуть бути виправлені окремим PR або ігноруватись.

### Request Changes

Є [blocker] або декілька [must-fix] коментарів. Автор повинен виправити та запросити повторне рев'ю.

### Comment

Є питання або пропозиції, але ти не блокуєш мерж. Використовуй, коли хочеш обговорити підхід.

> **Правило двох блокерів**
> Якщо в PR є 2+ blocker-и — зупини рев'ю, напиши загальний коментар і поверни автору. Немає сенсу вичитувати весь PR, якщо основа потребує переробки.

## 8. Антипатерни рев'ю

| Антипатерн | Чому це погано |
|---|---|
| **«Rubber-stamp» рев'ю** | Approve без коментарів за 2 хвилини. Ти не рев'юїш — ти просто натискаєш кнопку. |
| **Gatekeeping** | Блокування PR через особисті преференції стилю. Якщо це не в style guide — не блокуй. |
| **Rewrite пропозиції** | «Я б написав це інакше» без пояснення, чому інакше краще. Не пропонуй переписувати, якщо наявне рішення працює. |
| **Затягування** | Тримати PR в рев'ю більше 2 днів без реакції. Це вбиває продуктивність автора. |
| **Scope creep** | «А ще зроби ось це» — додаткові задачі, які не входять у scope PR. Створи окремий тікет. |
| **Емоційні коментарі** | «Це жахливо», «хто так пише?» — деструктивно і непрофесійно. |

---

## 9. Фінальний чекліст рев'ювера

Перед тим як натиснути Approve або Request Changes, пройдись по цьому списку:

- [ ] Я зрозумів задачу та acceptance criteria
- [ ] CI/CD пройшов успішно
- [ ] Код вирішує задачу, а не щось інше
- [ ] Edge cases оброблені
- [ ] Немає очевидних багів або race conditions
- [ ] Типізація адекватна (без зайвих any)
- [ ] Назви зрозумілі без контексту
- [ ] Тести покривають основні сценарії
- [ ] Немає security-проблем (XSS, витік даних)
- [ ] Мої коментарі конструктивні та з префіксами
