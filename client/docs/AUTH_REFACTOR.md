# Рефакторинг auth-потоку: що змінено і чому

## A) Що було не так, що змінено, чому така архітектура краща

### Що було не так

1. **Роутинг і призначення layout**
   - У `(auth)/layout.tsx` експортувався не layout, а повноцінна сторінка Sign Up (компонент із пропами `disableCustomTheme`).
   - Next.js очікує від layout сигнатуру `(props: { children: React.ReactNode }) => ReactNode`. Через це виникала помилка типів і некоректна робота вкладок auth.
   - Окремих маршрутів `/sign-in` та `/sign-up` не існувало; усі auth-екрани показували один і той самий Sign Up UI.

2. **Один компонент замість двох сторінок**
   - Логіка "логін" і "реєстрація" була змішана в одному файлі (layout як форма реєстрації).
   - Умови типу "показати логін або реєстрацію" в одному компоненті не було, але й окремих сторінок теж не було — тобто не було розділення потоків Sign In і Sign Up.

3. **Помилки в коді**
   - У формі Sign Up використовувалися `setEmailError` / `setPasswordError` без оголошення відповідного state (були лише `nameError` / `nameErrorMessage`).
   - Посилання "Sign in" вело на зовнішній URL (`/material-ui/getting-started/templates/sign-in/`) замість внутрішнього `/sign-in`.
   - Кнопка Submit викликала `validateInputs` через `onClick` замість валідації в `onSubmit` форми, що порушує семантику форми та доступність.

4. **Дублювання та мертвий код**
   - Компонент `RegisterForm` містив некоректну логіку (FormData на верхньому рівні, валідація під час рендеру, неоголошені змінні) і не використовувався коректно. Він видалений як мертвий код.

5. **Навігація**
   - Не використовувався Next.js `Link` для клієнтської навігації; посилання на "Sign in" вели на зовнішній шаблон, що могло викликати повне перезавантаження сторінки замість клієнтського переходу.

### Що змінено

1. **Роутинг**
   - Додано два незалежні маршрути: **`/sign-in`** та **`/sign-up`**.
   - `(auth)/layout.tsx` перероблено на справжній layout: приймає `children`, рендерить `AppTheme`, `CssBaseline`, `ColorModeSelect` і спільний контейнер `AuthContainer` навколо `children`. Жодної форми чи умовного перемикання логін/реєстрація в layout немає.

2. **Структура компонентів**
   - Дві окремі сторінки: **SignInPage** (`(auth)/sign-in/page.tsx`) та **SignUpPage** (`(auth)/sign-up/page.tsx`).
   - Спільний UI винесено в перевикористовувані компоненти:
     - `AuthContainer` — повноекранний контейнер з фоном.
     - `AuthCard` — картка форми.
     - `SocialAuthButtons` — блок "or" + кнопки Google/Facebook (проп `variant: 'signin' | 'signup'` для тексту).
     - `AuthFooterLink` — рядок з посиланням ("Don't have an account? Sign up" / "Already have an account? Sign in") через Next.js `Link`.

3. **Стан і валідація**
   - У Sign In: окремий state для `emailError`, `emailErrorMessage`, `passwordError`, `passwordErrorMessage`; валідація тільки в `onSubmit` (через FormData), без звернень до `document.getElementById`.
   - У Sign Up: окремий state для `nameError`, `nameErrorMessage` та полів email/password; та сама схема — валідація лише в `onSubmit`. Стан між формами не перетікає.

4. **Навігація**
   - Посилання між сторінками реалізовано через `next/link` і `AuthFooterLink`: "Already have an account? Sign in" → `/sign-in`, "Don't have an account? Sign up" → `/sign-up`. Кліки не викликають повного перезавантаження сторінки.

5. **Очищення**
   - Видалено старий вміст layout (форму Sign Up і всю пов’язану логіку).
   - Видалено зламаний `RegisterForm`.
   - Головна сторінка (`app/page.tsx`) більше не імпортує layout як "SignUp"; показує картку "Admin Panel Ready" з кнопками "Sign in" та "Sign up", які ведуть на `/sign-in` та `/sign-up`.

6. **UX і доступність**
   - Кнопки сабміту мають `type="submit"`, валідація прив’язана до `onSubmit` форми.
   - Соціальні кнопки мають `type="button"`, щоб не сабмітити форму.
   - Унікальні `id` полів (наприклад `signin-email`, `signup-name`) уникли конфліктів при наявності обох форм в DOM (на різних сторінках).

7. **Логіка авторизації**
   - Як і потрібно: реалізовано лише UI (форми, валідація, навігація). Виклики API логіну/реєстрації, збереження токенів, контекст авторизації не реалізовувалися.

### Чому така архітектура краща

- **Чіткі URL:** `/sign-in` і `/sign-up` дають зрозумілу структуру та можливість окремо кешувати, шарити та захищати маршрути.
- **Один layout для auth:** спільний вигляд (тема, фон, контейнер) без дублювання коду; зміна layout не вимагає правок у двох місцях.
- **Розділення відповідальності:** layout тільки обгортає, сторінки — форми та валідація, спільні частини — в окремих компонентах. Легше тестувати і змінювати окремі потоки.
- **Немає перетікання стану:** кожна сторінка має власний state і валідацію, що зменшує ризик багів при переході між Sign In і Sign Up.
- **Коректна робота з Next.js:** layout відповідає очікуваній сигнатурі, використовується App Router і клієнтська навігація через `Link`.

## B) Короткий огляд архітектури нового auth

```
app/
  (auth)/
    layout.tsx          → Client layout: AppTheme, CssBaseline, ColorModeSelect, AuthContainer; рендерить children
    sign-in/
      page.tsx          → SignInPage (email, password, Remember me, Forgot password?, кнопка Sign in, соціальні кнопки, посилання на /sign-up)
    sign-up/
      page.tsx          → SignUpPage (name, email, password, checkbox updates, кнопка Sign up, соціальні кнопки, посилання на /sign-in)
  page.tsx              → Головна: картка з кнопками "Sign in" (/sign-in) та "Sign up" (/sign-up)

components/auth/
  AuthContainer.tsx     → Стилізований Stack (повна висота, фон); використовується в (auth)/layout
  AuthCard.tsx          → Стилізована Card; використовується в обох сторінках
  SocialAuthButtons.tsx → "or" + Google/Facebook кнопки; variant: 'signin' | 'signup'
  AuthFooterLink.tsx    → Текст + посилання (Next.js Link); пропси text, linkText, href
```

- **Потік:** Користувач потрапляє на `/` → обирає "Sign in" або "Sign up" → переходить на `/sign-in` або `/sign-up`. На цих сторінках через футер може перейти на іншу auth-сторінку без перезавантаження.
- **Стан:** Кожна сторінка зберігає лише власні помилки валідації та не передає їх в інші сторінки.
- **Спільний код:** Тема, фон, картка, соціальні кнопки та блок посилання винесені в компоненти; форми та валідація залишаються на сторінках.

## C) Можливі покращення для production

1. **Логіка авторизації:** Підключити реальні виклики API (login/register), обробку помилок, збереження токенів (наприклад httpOnly cookies) та контекст/стан "поточний користувач". Редирект після успішного логіну/реєстрації на дашборд або на захищені маршрути.

2. **Захист маршрутів:** Middleware або перевірка в layout дашборду: якщо користувач не авторизований і заходить на захищену сторінку — редірект на `/sign-in`. Якщо вже авторизований і заходить на `/sign-in` або `/sign-up` — редірект на головну або дашборд.

3. **Форми та валідація:** Перехід на React Hook Form + Zod (або іншу схему) для єдиної схеми валідації, кращих повідомлень про помилки та меншого ручного state.

4. **Loading та глобальні помилки:** Стан завантаження (наприклад `isSubmitting`) на кнопці сабміту, можливо глобальний стан помилки від API (snackbar/toast) без перетікання між сторінками.

5. **Forgot password:** Окрема сторінка `/forgot-password` або модалка; посилання "Forgot your password?" на Sign In вести на неї замість `#`.

6. **Тести:** Unit-тести валідації та інтеграційні/e2e тести сценаріїв: перехід sign-in → sign-up, сабміт форми, відображення помилок.

7. **a11y та семантика:** Переконатися, що форми мають коректні `aria-*`, пов’язані з лейблами; повідомлення про помилки доступні для скрінрідерів.

8. **Типизація:** Спільні типи для тіл запитів/відповідей логіну та реєстрації (наприклад з OpenAPI або спільного пакету з бекендом).
